# Phase 4 — Memory v4: Retrieval audit UI

## Goal

Make the data Phase 1 + 2 started writing visible. Two surfaces:

1. **Retrievals tab** in the agent harness modal — paginated timeline of `memory_retrieved` + `project_memory_retrieved` events, showing trigger query and retrieved keys + cosine scores per run.
2. **Memory list audit badges** — each memory row in the harness shows "pulled into N runs / 30d" with a hover-tooltip listing the last 3 retrieval timestamps + scores.

## Non-goals

- **Replacing the existing Activity tab.** It still shows everything. Retrievals is a focused view, not a replacement.
- **Per-tenant cross-agent dashboard.** A "which memories does the whole project rely on?" surface is interesting but out of scope; Phase 4 stays per-agent.
- **Modifying memory rows from the audit view** (e.g. "stale this row" or "boost this row"). The Memory tab is where edits happen.

## Tasks

### 4.1 — Activity endpoint extension
- `src/app/api/agents/[id]/activity/route.ts` — add `?type=a,b,c` filter + `?before=<ISO>` cursor pagination. Existing callers (no params) get exactly the same response.

### 4.2 — Retrievals tab
- `src/components/agents/AgentHarnessModal.tsx` — new `'retrievals'` Tab + `RetrievalsPanel` component. Fetches the new endpoint with `type=memory_retrieved,project_memory_retrieved`. Renders timestamp, tier badge (color-coded agent vs project), trigger query, and per-key chips with cosine score. "Load older" button uses `before=` cursor.

### 4.3 — Memory list audit badges
- Same modal — `MemoryPanel` extended to fetch the last 100 `memory_retrieved` events on load and aggregate them into a per-key map. Each memory row gets a "N pulls / 30d" chip when count > 0; hover shows last 3 timestamps + scores via the native `title` attribute.
- Aggregation logic extracted to `src/lib/retrievalAudit.ts` (pure, testable).

### 4.4 — Tests
- `tests/compat/retrieval-audit.test.ts` — 7 cases on `aggregateRetrievalsByKey`. Endpoint route tests deferred (auth() mocking friction; consistent with existing testing posture).

### 4.5 — Docs
- This file. Plus `04-01-SUMMARY.md` after work lands. STATE.md Prior Work table extended.

## Risks + mitigations

- **Risk:** The retrievals fetch in MemoryPanel doubles the load time of the Memory tab.
  **Mitigation:** Two `fetch`es fire concurrently; aggregation happens in O(events) time. For 100 events, sub-millisecond. Tab still renders in < 100ms.

- **Risk:** Aggregation logic embedded in a React component is hard to maintain.
  **Mitigation:** Extracted to `src/lib/retrievalAudit.ts` with parameter-injectable `now` and `windowMs` so it's deterministically testable.

- **Risk:** UI gets re-done by M1 Phase 3 audit work.
  **Mitigation:** Documented; data model is reusable.

## Success criteria

- [ ] `npx tsc --noEmit` clean.
- [ ] `npm test` ≥ 94 (was 87 + 7 audit = 94).
- [ ] Existing activity endpoint callers (no params) get unchanged responses.
- [ ] Aggregation handles malformed payloads (null payload, missing keys, invalid createdAt) without throwing.
- [ ] Retrievals tab renders with correct fields when there's at least one `memory_retrieved` event in the activity log (manual UI smoke).
