# Phase 3 — Memory v3: Lifecycle (dedup + stale flag)

## Goal

Give agent + project memory a maintenance layer so accumulated rows don't bloat the prompt or harbor near-duplicates. Three operations:

1. **Dedup** — collapse pairs of rows with cosine similarity > 0.92 and matching `kind`. Keep the newer `updatedAt`, merge `sourceRef` values.
2. **Stale flag** — flag `kind='context'` `AgentMemory` rows that haven't been retrieved in 90 days. Stale rows drop out of `compileHarness` retrieval immediately.
3. **Summary** — read-only counts (total / embedded / stale / dedupCandidates) for the audit UI.

## Why now

Memory accumulates. Without lifecycle ops, agents end up with redundant entries (same fact stated three different ways) and stale context riding in the prompt long after it stopped being relevant. claude-os solves this with dedup + archival; we adopt the minimum slice that earns its keep without a Python sidecar.

## Non-goals

- **Scheduled auto-tick.** The plan in the original ROADMAP listed a nightly job in `src/lib/scheduler/`. **Deferred.** Manual trigger endpoints cover the immediate need (admins curl them; or wire to system cron). Memory volume isn't yet at a level where automation is critical, and the scheduler integration adds 30+ min of cross-feature risk.
- **Stale-marking on `ProjectMemory`.** The `stale` column exists for symmetry + manual harness toggle (Phase 4), but no automatic pass — the project tier has no `kind='context'` (only decision/glossary/convention/fact, which don't decay on the 90d cadence).
- **LLM-driven consolidation** (synthesizing N near-duplicates into a single new row). Expensive + brittle. Sticking with last-writer-wins + sourceRef merge.

### Task 3.2 — Lifecycle module

`src/lib/memoryLifecycle.ts` — five exports:
- `dedupAgentMemory(agentId): Promise<DedupResult>`
- `dedupProjectMemory(projectId): Promise<DedupResult>`
- `markStaleAgentMemories(agentId): Promise<{ marked: number }>`
- `agentMemorySummary(agentId): Promise<MemorySummary>`
- `projectMemorySummary(projectId): Promise<MemorySummary>`

Plus constants `DEDUP_COSINE_THRESHOLD = 0.92` and `STALE_AGE_DAYS = 90`.

### Task 3.3 — Wire stale exclusion + lastRetrievedAt update into retrieval

`src/lib/agentHarness.ts:retrieveMemories` and `:retrieveProjectMemories` — every path (fallback findMany + ranked CTE + prefs CTE + recent_decisions CTE) filters `stale = false`. After every retrieval, batched `updateMany` bumps `lastRetrievedAt` on the retrieved ids. Bump runs in parallel with the activity log write on the vector path.

### Task 3.4 — Manual lifecycle trigger endpoints

- `POST /api/agents/[id]/memory/lifecycle` — runs `dedupAgentMemory` + `markStaleAgentMemories`, logs `memory_lifecycle_run` event.
- `POST /api/projects/[id]/memory/lifecycle` — runs `dedupProjectMemory` only (no stale pass for project tier).

### Task 3.5 — Summary endpoints

- `GET /api/agents/[id]/memory/summary`
- `GET /api/projects/[id]/memory/summary`

Read-only `{ total, embedded, stale, dedupCandidates }`. The `dedupCandidates` field is a "would dedup do anything?" preview — runs the same JOIN as dedup but doesn't mutate.

## Risks + mitigations

- **Risk:** Dedup overrun — large memories with many near-duplicates produce a huge pair set.
  **Mitigation:** Postgres handles the JOIN; the JS layer iterates pairs in similarity-desc order and dedups greedily. For agents with O(10⁴) memories, the pair count stays bounded by similarity threshold (0.92 is tight enough that random pairs don't qualify).

- **Risk:** Stale-marking races with retrieval.
  **Mitigation:** stale-marking is a write; retrieval reads. Postgres MVCC handles the visibility correctly. Worst case: a row that just got stale-marked gets retrieved one more time before the new visibility propagates. Acceptable.

- **Risk:** lastRetrievedAt write amp on every retrieval.
  **Mitigation:** Batched `updateMany` with `id: { in: ids }` is one round-trip per retrieval. For an agent with 1000 rows, worst case ~50ms. Acceptable.

- **Risk:** Phase 4 "audit UI" overlaps with M1 Phase 3 audit surfaces.
  **Mitigation:** Documented in M1 ROADMAP. If overlap creates rework, accept it — the data model (`memory_retrieved` / `project_memory_retrieved` / `memory_lifecycle_run` events) is reusable across whichever UI lands.
