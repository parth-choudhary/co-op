# Plan 01-02 — HarnessSnapshot + deterministic harness split

## Goal

Make harness assembly deterministic and snapshottable. Three mechanical changes:

1. **Extend `HarnessSnapshot`** with the columns that capture exactly what the agent saw at run start: compiled prompt, tool schema, plugin allowlist, run-mode flag, agent state hash, project state hash, captured-at timestamp.
2. **Split `agentHarness.ts:compileHarness`** into:
   - `buildHarness(inputs)`: pure function. No DB reads, no `Date.now()`, no `process.env`. All inputs are parameters.
   - `snapshotHarness(agentId, ctx, now)`: impure wrapper. Reads agent + project state, calls `buildHarness`, writes a `HarnessSnapshot` row, returns its id.
3. **`harnessInputs.ts`**: a small module whose only job is to load `AgentStateAtStart` and `ProjectStateAtStart` from the DB given an agent id. This is the impure boundary; tests stub this layer to feed deterministic inputs into `buildHarness`.

This plan does NOT change `runAgent` or `compileHarness` callers. Both old and new code paths coexist after this plan ships. Phase 2 is where the runner switches to `snapshotHarness` at run start.

## Why split this way

`compileHarness` today (`src/lib/agentHarness.ts:280`) does three things in one async function: load agent + project from DB, call retrieveMemories / retrieveProjectMemories (which embed via OpenAI — non-deterministic), and assemble the prompt. The retrieval calls are SDK-bound and time-sensitive; the prompt assembly is what we want pure.

We can't make retrieval deterministic without freezing the embedding model — out of scope. So the determinism contract is: **given the same retrieved memory set + same agent state + same project state + same ctx, `buildHarness` produces byte-identical output.** The snapshot captures the retrieved memory set as part of the "captured inputs" so a resume sees the same memories the original run saw.

### Task 01-02.2 — Define HarnessInputs + extract loaders

**Files:** `src/lib/harnessInputs.ts` (new)

**Action:**

```ts
import prisma from './db';
import { retrieveMemories, retrieveProjectMemories } from './agentHarness';
import type { HarnessContext } from './agentHarness';

// The full input set buildHarness consumes. Every field is concrete data,
// no Promises, no DB clients. Hashing this object should produce a stable
// identifier; deeply equal inputs produce identical outputs.
export interface HarnessInputs {
  agent: {
    id: string;
    name: string;
    role: string;
    roleLabel: string;
    description: string | null;
    systemPrompt: string;
    soulMd: string | null;
    plugins: string[];
    projectId: string | null;
    runMode: 'read-only' | 'propose-only' | 'propose-and-execute';
  };
  project: {
    name: string;
    about: string | null;
    aboutUpdatedAt: Date | null;
    userMd: string | null;
    userMdUpdatedAt: Date | null;
    agentsMd: string | null;
    agentsMdUpdatedAt: Date | null;
  } | null;
  agentMemories: Array<{ key: string; content: string; kind: string }>;
  projectMemories: Array<{ key: string; content: string; kind: string }>;
  recentActivity: Array<{ eventType: string; payload: any; createdAt: Date }>;
  kanban: any; // shape unchanged from current code; type stays opaque to keep the diff small
  ctx: HarnessContext;
  now: Date;
}

export async function loadHarnessInputs(agentId: string, ctx: HarnessContext, now: Date): Promise<HarnessInputs> {
  const agent = await prisma.aIAgent.findUnique({ where: { id: agentId } });
  if (!agent) throw new Error('Agent not found');

  const [project, agentMemories, projectMemories, recentActivity, kanban] = await Promise.all([
    agent.projectId ? prisma.project.findUnique({
      where: { id: agent.projectId },
      select: { name: true, about: true, aboutUpdatedAt: true, userMd: true, userMdUpdatedAt: true, agentsMd: true, agentsMdUpdatedAt: true },
    }) : Promise.resolve(null),
    retrieveMemories(agentId, ctx.triggerText),
    agent.projectId
      ? retrieveProjectMemories(agentId, agent.projectId, ctx.triggerText)
      : Promise.resolve([]),
    prisma.agentActivityLog.findMany({ where: { agentId }, orderBy: { createdAt: 'desc' }, take: 20 }),
    // getAgentKanbanContext lives in agentHarness today; the refactor moves it into harnessInputs.ts
    // OR re-exports it. Keep import boundary clean: re-export.
    (await import('./agentHarness')).getAgentKanbanContext(agentId),
  ]);

  return {
    agent: {
      id: agent.id, name: agent.name, role: agent.role, roleLabel: agent.roleLabel,
      description: agent.description, systemPrompt: agent.systemPrompt,
      soulMd: agent.soulMd, plugins: agent.plugins, projectId: agent.projectId,
      runMode: 'propose-and-execute', // Phase 2 reads from agent.runMode column once it exists
    },
    project,
    agentMemories: agentMemories.map(m => ({ key: m.key, content: m.content, kind: m.kind })),
    projectMemories: projectMemories.map(m => ({ key: m.key, content: m.content, kind: m.kind })),
    recentActivity,
    kanban,
    ctx,
    now,
  };
}
```

**Verify:** `npx tsc --noEmit` clean. `loadHarnessInputs(agentId, {kind: 'chat', triggerText: 'hi'}, new Date())` returns a fully-populated input object for an existing agent.

**Done:** atomic commit `feat(run): harnessInputs.ts — explicit DB loader for buildHarness`.

### Task 01-02.3 — Refactor compileHarness into buildHarness + snapshotHarness

**Files:** `src/lib/agentHarness.ts`

**Action:** This is the biggest mechanical change in Phase 1. Three steps:

1. **Extract** the body of the current `compileHarness` (after the parallel fetch) into a new pure function `buildHarness(inputs: HarnessInputs): { compiledPrompt: string; toolSchema: any; pluginAllowlist: string[]; runMode: string }`. The return is the four fields that go into the snapshot.

2. **Add** `snapshotHarness(agentId, ctx, now)`:
   ```ts
   import { createHash } from 'node:crypto';
   import { loadHarnessInputs } from './harnessInputs';

   export async function snapshotHarness(agentId: string, ctx: HarnessContext, now: Date = new Date()): Promise<string> {
     const inputs = await loadHarnessInputs(agentId, ctx, now);
     const built = buildHarness(inputs);
     const agentStateHash = createHash('sha256').update(JSON.stringify(inputs.agent)).digest('hex');
     const projectStateHash = inputs.project ? createHash('sha256').update(JSON.stringify(inputs.project)).digest('hex') : null;
     const snap = await prisma.harnessSnapshot.create({
       data: {
         agentId,
         compiledPrompt: built.compiledPrompt,
         toolSchema: built.toolSchema,
         pluginAllowlist: built.pluginAllowlist,
         runMode: built.runMode,
         agentStateHash, projectStateHash,
         retrievedMemories: { agentMemories: inputs.agentMemories, projectMemories: inputs.projectMemories },
         capturedAt: now,
       },
     });
     return snap.id;
   }
   ```

3. **Keep** the existing `compileHarness(agentId, ctx)` as a thin wrapper that calls `snapshotHarness` and returns the compiled prompt string — preserves the current callers (`agentRunner.ts:136`, `agents/[id]/context/route.ts`). Mark it `@deprecated` in the JSDoc; Phase 2 migrates `runAgent` to `snapshotHarness` directly so the runner can store the snapshot id on the run.

**Verify:**
- `compileHarness('agent-1', {kind: 'chat', triggerText: 'foo'})` continues to return a string identical (modulo the `now` timestamp wherever it surfaces) to the pre-refactor output. Use `harness-isolation.test.ts` as the diff baseline.
- `snapshotHarness('agent-1', ctx, fixedDate)` writes a HarnessSnapshot row with all fields populated.
- `buildHarness(inputs)` called twice with the same `inputs` produces identical strings (test in 01-02.4).

**Done:** atomic commit `feat(run): split compileHarness → buildHarness (pure) + snapshotHarness (writer)`.

### Task 01-02.4 — Determinism test

**Files:** `tests/compat/harness-determinism.test.ts` (new)

**Action:** Construct a fixed `HarnessInputs` (no DB, no clock) and assert two `buildHarness(inputs)` calls return identical strings + identical `toolSchema` JSON. Vary `inputs.now` (so the test fixes a known timestamp), vary `inputs.agentMemories` order — even reordered memories should yield identical output (since the harness already sorts by kind). Mutate one field and assert the output diverges.

5 test cases:
1. Same inputs → identical output (the determinism contract).
2. Different `now` → output may differ ONLY at timestamp insertions (currently none in `buildHarness`; if a future change adds one, this test catches it).
3. Memory list reordering → identical output (sort is stable inside `buildHarness`).
4. Different agent.systemPrompt → divergent output, on the systemPrompt section.
5. ProjectMemories empty vs populated → presence/absence of `## Project Memory` block.

**Verify:** `npm test` total ≥ 104 (was 99 + 5 = 104).

## Risks + mitigations

- **Risk:** Refactoring `compileHarness` breaks the existing `harness-isolation.test.ts` (which monkey-patches `dbModule`).
  **Mitigation:** Keep `compileHarness` as a wrapper that internally calls the new functions; existing test mocks (`agentMemory.findMany`, `projectMemory.findMany`, etc.) still satisfy the data path. Re-run `npm test` after each commit in this plan.
- **Risk:** Hashing `JSON.stringify(inputs.agent)` produces unstable output if Prisma returns object keys in non-deterministic order.
  **Mitigation:** Stable-stringify with `Object.keys(...).sort()` before hashing. Add a test that asserts hash is stable across two loads of the same agent.
- **Risk:** `snapshotHarness` writes a row on every call → table bloat for runs that get aborted before doing work.
  **Mitigation:** Phase 1 documents this; Phase 2 will only call `snapshotHarness` from the runner, after run-start commits. Manual test calls of `compileHarness` from API endpoints (the debug `/context` endpoint) shouldn't snapshot — split: `compileHarness` doesn't snapshot, `snapshotHarness` does.
