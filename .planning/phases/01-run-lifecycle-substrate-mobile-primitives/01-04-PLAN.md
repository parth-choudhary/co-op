# Plan 01-04 — Mobile primitives

## Goal

Establish the mobile UI primitives every later UI phase consumes:
1. Viewport meta + breakpoint tokens + safe-area helpers (the foundations).
2. Vaul-backed `Drawer` (sidebar replacement) + `BottomSheet` (modal replacement) components.
3. A small `useViewportLte('md')` hook so any component can react to the current breakpoint.
4. A PWA manifest making the app installable to home screen on iOS Safari + Android Chrome.
5. Two consumers wired up — `Sidebar` collapses into the Drawer at <768px; `CardDetailModal` renders as a BottomSheet at <768px — as proof the primitives work end-to-end.

This plan ships **no responsive sweep** of existing screens beyond the two consumers above. Phase 3 (AUD + MOB-09..11) does the full audit.

## Why this is independent of the backend tracks

01-01 / 01-02 / 01-03 touch the runtime + db. This plan touches `src/app/layout.tsx`, `src/styles/`, `src/components/layout/Sidebar.tsx`, `src/components/kanban/CardDetailModal.tsx`, plus four new component files. No overlap. Can land first or last with no dependency on the other plans.

### Task 01-04.3 — useViewportLte hook + Drawer + BottomSheet components

**Files:**

**Action:**

`useViewportLte.ts`:

```ts
'use client';
import { useEffect, useState } from 'react';

const BREAKPOINTS = { sm: 480, md: 768, lg: 1024 } as const;

export function useViewportLte(bp: keyof typeof BREAKPOINTS): boolean {
  const [matches, setMatches] = useState(false);
  useEffect(() => {
    const mql = window.matchMedia(`(max-width: ${BREAKPOINTS[bp] - 1}px)`);
    const update = () => setMatches(mql.matches);
    update();
    mql.addEventListener('change', update);
    return () => mql.removeEventListener('change', update);
  }, [bp]);
  return matches;
}
```

`Drawer.tsx` and `BottomSheet.tsx` — thin wrappers around `vaul`'s `Drawer` primitive, configured for our two use-cases:

- **Drawer**: side-drawer for mobile sidebar. Direction='left'; backdrop dismiss; ESC dismiss; swipe-to-close enabled; `prefers-reduced-motion` honored (vaul handles this natively).
- **BottomSheet**: bottom-anchored sheet for mobile modals. Sticky header (close button), sticky footer (primary action slot), scrollable content between. `dismissible` defaults to true; pass-through for `onClose` handler.

Each wrapper exposes a small typed interface so consumers don't import vaul directly:

```ts
export interface BottomSheetProps {
  open: boolean;
  onClose: () => void;
  title: string;
  primaryAction?: { label: string; onClick: () => void; disabled?: boolean };
  children: React.ReactNode;
}
export function BottomSheet({ open, onClose, title, primaryAction, children }: BottomSheetProps) {
  // implementation per vaul docs; sticky header + sticky footer slot via flex layout
}
```

`MobileNav.tsx`: a thin component that renders the hamburger trigger + uses `Drawer` to wrap the sidebar contents. Consumed by the existing `Sidebar` in 01-04.4.

**Verify:** A scratch story page (or a test fixture) renders Drawer + BottomSheet without crashing. Drawer dismiss-on-backdrop and BottomSheet swipe-down-to-close both work in Chrome devtools mobile mode.

### Task 01-04.5 — BottomTabBar component + project shell integration

**Files:**
- `src/components/mobile/BottomTabBar.tsx` (new)
- `src/app/(dashboard)/p/[projectId]/layout.tsx` (existing — render the tab bar at `<768px`)

**Action:**

`BottomTabBar.tsx` — a fixed-position bottom nav that renders three tabs (Plans / Runs / Chat). Per CONTEXT D-04 + D-05, tabs are **current-project scoped**: each tab links into a project-scoped route (`/p/[projectId]/plans`, `/p/[projectId]/runs`, `/p/[projectId]/chat`). When no project is in the URL params, the tab bar is rendered hidden OR as an empty "Pick a project" state pointing at the Drawer.

```tsx
'use client';
import Link from 'next/link';
import { usePathname, useParams } from 'next/navigation';
import { ListChecks, Activity, MessageSquare } from 'lucide-react';

// Exactly the three tabs CONTEXT D-04 locked. Adding a fourth here is a
// scope change that needs to amend the phase plan, not a drive-by edit.
const TABS = [
  { key: 'plans', label: 'Plans', icon: ListChecks, hrefSegment: 'plans' },
  { key: 'runs',  label: 'Runs',  icon: Activity,    hrefSegment: 'runs'  },
  { key: 'chat',  label: 'Chat',  icon: MessageSquare, hrefSegment: 'chat' },
] as const;

export function BottomTabBar() {
  const params = useParams<{ projectId?: string }>();
  const pathname = usePathname();
  const projectId = params.projectId;
  if (!projectId) return null; // Outside a project route — hidden; "Pick a project" state lives in /m primary view, NOT here

  return (
    <nav
      role="navigation"
      aria-label="Primary"
      className="bottom-tab-bar"
      style={{
        // Fixed bottom; safe-area-aware for iOS home indicator.
        position: 'fixed',
        left: 0, right: 0, bottom: 0,
        paddingBottom: 'var(--safe-bottom)',
        // Hide at ≥768px (the project shell hides via container query / media query).
      }}
    >
      {TABS.map(t => {
        const href = `/p/${projectId}/${t.hrefSegment}`;
        const active = pathname.startsWith(href);
        return (
          <Link key={t.key} href={href} aria-current={active ? 'page' : undefined} className={active ? 'active' : ''}>
            <t.icon size={20} />
            <span>{t.label}</span>
          </Link>
        );
      })}
    </nav>
  );
}
```

The hide-at-≥768px behavior happens in CSS — a `@media (min-width: 768px) { .bottom-tab-bar { display: none } }` rule alongside the component, so SSR doesn't have to know the breakpoint. Touch targets ≥44pt per MOB-09 (Phase 3 audit will verify; tab cells should already meet this).

`p/[projectId]/layout.tsx` — render `<BottomTabBar />` once at the project shell level. Inserts it as a sibling of the existing main content; bottom-padding on the main scroll container clears the tab bar height + safe-area on phone.

**Routing note:** `/p/[projectId]/plans` and `/p/[projectId]/runs` don't yet exist in M1 (they ship in P3 + P4 respectively). For Phase 1, the BottomTabBar links to those routes anyway — Next.js will 404 until those routes land, which is correct behavior. Tab bar UI is the deliverable; route content is later phases.

**Verify:**
- At 375×667 inside `/p/[projectId]/...`, the tab bar is visible at the bottom with three tabs.
- At ≥768px on the same route, the tab bar is hidden.
- Active-state styling lights up the tab matching the current path prefix.
- Outside a project route, the tab bar is not rendered.
- Touch target (the link's bounding box) measures ≥44×44pt at default font size.
- No mobile typography overrides land in tokens.css (D-02 audit).

**Done:** atomic commit `feat(mobile): BottomTabBar — Plans/Runs/Chat tabs, project-scoped, hidden ≥768px`.

## Risks + mitigations

- **Risk:** Vaul + framer-motion peer-dep conflict with React 19.
  **Mitigation:** Research SUMMARY.md verified `vaul ^1.1.2` is React 19-compatible. If install fails, downgrade to a known-good minor; do NOT introduce `react-spring` (anti-pattern per research).
- **Risk:** Sidebar refactor breaks existing desktop layout subtly.
  **Mitigation:** Visual diff against pre-PR screenshots at 1280×800. Sidebar rendering at `≥768px` keeps the original code path unchanged via `isMobile ? Drawer : Static` ternary.
- **Risk:** PWA manifest + iOS Add-to-Home-Screen are finicky about icon sizes.
  **Mitigation:** Ship 192/512/180 baseline; iOS-specific `apple-touch-icon` link in `app/layout.tsx`. Real-device test on iPhone Safari + Android Chrome before merging.
- **Risk:** `useViewportLte` mismatches SSR (server renders matching=false; first client render flashes layout).
  **Mitigation:** Initial state is `false` — desktop rendering on server. Layout flash on hydration is acceptable for v1; `next/script` w/ inline media-query check is a Phase 3 polish if it becomes annoying.
