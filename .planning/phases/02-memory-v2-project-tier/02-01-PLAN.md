# Phase 2 — Memory v2: Project-tier shared memory

## Goal

Add a project-scoped memory tier above the per-agent memory we built in Phase 1. Agents in the same project share a learned brain instead of each rediscovering the same decisions, conventions, and glossary. Humans can also browse + edit project memory from project settings.

The implementation reuses **everything** from Phase 1: same embedding wrapper, same retrieval pattern, same fallback semantics. ProjectMemory is structurally a sibling of AgentMemory, not a rewrite.

## Why now

Co-Op's `Project.about` / `userMd` / `agentsMd` are admin-only free-text fields — a coarse, manually-maintained shared brain. Agents writing to them would be too heavy (one agent's stray observation could overwrite another's careful framing) and they're not searchable. ProjectMemory is the structured, searchable, agent-writable layer that closes the gap. It also unblocks Phase 3 (lifecycle ops can dedup across both tiers) and Phase 4 (audit UI shows both per-agent + project retrievals in one view).

## Non-goals

- Cross-project search or "see all my project memory at once" UI. Each project's memory is isolated; the UI is per-project.
- Approval gating on agent writes. Like `AgentMemory`, project memory writes are immediate. If misuse becomes a problem, gate later — don't pre-emptively design for it.
- Replacing `Project.about` / `userMd` / `agentsMd`. Those stay; project memory is additive.
- Per-role auth (admin-only writes vs member writes). Any ProjectMember can read AND write. Simpler now; tighten later if needed.

### Task 2.1 — Add ProjectMemory model + migration

**Files:**
- `prisma/schema.prisma`
- `prisma/migrations/20260502010000_add_project_memory/migration.sql`

**Action:**

1. In `schema.prisma`, add the ProjectMemory model parallel to AgentMemory:
   ```prisma
   model ProjectMemory {
     id        String   @id @default(cuid())
     projectId String
     project   Project  @relation(fields: [projectId], references: [id], onDelete: Cascade)
     key       String
     content   String   @db.Text
     kind      String   @default("fact")     // 'decision' | 'glossary' | 'convention' | 'fact'
     source    String   @default("manual")   // 'agent' | 'admin' | 'manual'
     sourceRef String?
     writtenBy String?  // agentId — null for human-authored
     embedding Unsupported("vector(1536)")?
     createdAt DateTime @default(now())
     updatedAt DateTime @updatedAt

     @@unique([projectId, key])
     @@index([projectId])
     @@index([projectId, kind])
   }
   ```
2. Add `projectMemories ProjectMemory[]` to the Project model relations.
3. Hand-write the migration SQL (Prisma can't introspect `Unsupported("vector(1536)")` reliably for new tables — write it directly to match the schema and add the HNSW index in the same file):
   ```sql
   CREATE TABLE "ProjectMemory" (
     "id" TEXT NOT NULL,
     "projectId" TEXT NOT NULL,
     "key" TEXT NOT NULL,
     "content" TEXT NOT NULL,
     "kind" TEXT NOT NULL DEFAULT 'fact',
     "source" TEXT NOT NULL DEFAULT 'manual',
     "sourceRef" TEXT,
     "writtenBy" TEXT,
     "embedding" vector(1536),
     "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
     "updatedAt" TIMESTAMP(3) NOT NULL,
     CONSTRAINT "ProjectMemory_pkey" PRIMARY KEY ("id")
   );
   CREATE UNIQUE INDEX "ProjectMemory_projectId_key_key" ON "ProjectMemory"("projectId", "key");
   CREATE INDEX "ProjectMemory_projectId_idx" ON "ProjectMemory"("projectId");
   CREATE INDEX "ProjectMemory_projectId_kind_idx" ON "ProjectMemory"("projectId", "kind");
   CREATE INDEX "ProjectMemory_embedding_hnsw_cosine_idx" ON "ProjectMemory" USING hnsw ("embedding" vector_cosine_ops);
   ALTER TABLE "ProjectMemory" ADD CONSTRAINT "ProjectMemory_projectId_fkey" FOREIGN KEY ("projectId") REFERENCES "Project"("id") ON DELETE CASCADE ON UPDATE CASCADE;
   ```
4. Run `npx prisma migrate deploy` then `npx prisma generate`.

**Verify:**
- `docker compose exec -T db psql -U coop -d coop -c "\d \"ProjectMemory\""` shows the table with `embedding | vector(1536)` and the HNSW index.
- `npx tsc --noEmit` clean (Prisma client regen exposes `prisma.projectMemory`).

**Done:** atomic commit `feat(memory): add ProjectMemory model + pgvector index`.

### Task 2.4 — Wire project memory into compileHarness

**Files:**
- `src/lib/agentHarness.ts`

**Action:**

1. Add an exported `retrieveProjectMemories(projectId, triggerText)` helper modeled on `retrieveMemories`. Same three-source CTE — top-12 cosine + all preferences + recent decisions — but parameterized on `projectId` instead of `agentId`. Same fallback semantics.
2. Audit-log retrieval to `AgentActivityLog` (NOT a project-scoped log, since the audit is per-agent: which agent run loaded which project memories?). Use a new event type `project_memory_retrieved` parallel to `memory_retrieved`. Payload includes `projectId`, `retrieved: [{key, score}]`, `query`.
3. In `compileHarness`, after the existing per-agent memory section, add a **separate** Project Memory section so the model can distinguish "I learned this" from "we as a team learned this":
   ```ts
   if (agent.projectId) {
     const projectMemories = await retrieveProjectMemories(agent.projectId, ctx.triggerText);
     // (run in parallel with the existing Promise.all above — refactor that block to include this)
     if (projectMemories.length > 0) {
       parts.push('\n## Project Memory');
       parts.push('_(Shared with every agent in this project. Decisions, glossary, and conventions live here.)_');
       const byKind: Record<string, typeof projectMemories> = {};
       for (const m of projectMemories) (byKind[m.kind] ||= []).push(m);
       for (const [kind, items] of Object.entries(byKind)) {
         parts.push(`\n### ${kind}`);
         for (const m of items) parts.push(`- **${m.key}**: ${m.content}`);
       }
     }
   }
   ```
4. Refactor the top-of-function `Promise.all` to also await `retrieveProjectMemories` so we don't add a sequential round-trip.

**Verify:**

- For an agent with `projectId = null` (the rare `companyId`-only agent): output does NOT contain `## Project Memory` — section is suppressed.
- AgentActivityLog has both `memory_retrieved` (agent tier) and `project_memory_retrieved` (project tier) when both are non-empty and `OPENAI_API_KEY` is set.

## Risks + mitigations

- **Risk:** Project memory bloats the system prompt for agents in busy projects.
  **Mitigation:** Same retrieval ceiling as agent memory — top-12 ranked + always-include preferences + recent decisions. We get the same prompt-size guarantees we got in Phase 1.

- **Risk:** Two agents write conflicting project memories under the same key (race) — last-writer-wins overwrites the other.
  **Mitigation:** Prisma upsert is single-statement atomic; we rely on `(projectId, key)` uniqueness. If conflict resolution becomes a real problem, Phase 3's dedup pass will catch semantic duplicates after the fact. Don't pre-emptively introduce locking.

- **Risk:** Agent in one project somehow ends up writing to another project's memory (auth bypass).
  **Mitigation:** Tool handler resolves `agentId → projectId` server-side and refuses cross-project writes; Task 2.6 locks this in via test.

- **Risk:** `set_project_memory` becomes a noisy default — agents writing speculative or wrong "facts."
  **Mitigation:** The tool description (Task 2.3) explicitly distinguishes shared vs private memory. If misuse happens at runtime, Phase 3's dedup + stale flag is the cleanup mechanism. Don't gate writes pre-emptively.

- **Risk:** UI feels redundant with `Project.about` / `userMd` / `agentsMd`.
  **Mitigation:** The settings page intro should be one sentence: "Free-form team doctrine lives in About / USER.md / AGENTS.md. Project Memory is the structured, searchable layer agents read + write into automatically." Document once, in the UI, where users are looking.

## Success criteria

- [ ] `prisma migrate deploy` succeeds against the existing pgvector container.
- [ ] Two agents in one project, neither having seen each other's history, both surface a `kind='decision'` project memory written by a third agent.
- [ ] An agent in a different project does NOT see another project's memory (verified by Task 2.6 test, not just manual check).
- [ ] Project memory writes show in `AgentActivityLog` with `writtenBy = agentId` traceable.
- [ ] No regression in Phase 1 behavior (existing agent-memory tests still pass).
- [ ] `npm test` total: ≥ 81 (73 today + 4 auth + 4 keyless = 81).
- [ ] No UI changes outside the new `settings/memory/page.tsx` and modal.
- [ ] Keyless deployments behave identically to today on both tiers.
